## Arquitetura e lifecycle

```text
Execution Broker → PTY reader → replay bounded + live cursor wakeup
                                         ↓
HumanTerminal registry             Presentation worker
                                         ↓ raw Channel
                                      xterm

OperationalTraceBus → replay + live subscriber → Presentation worker
                                         ↓ coalesce_batch + DTO + Channel
                                      TraceStore → filtros → viewport
```

`execution/human.rs` mantém o único registry humano de produto process-wide via
OnceLock/Arc, ligado ao Broker aprovado. O managed state não nasce com uma PTY.
`open()` só é invocado pelo gesto **Iniciar terminal local**; reencontra uma
sessão starting/running/cleanup_pending existente. Um handle terminal é substituído
quando uma nova sessão é explicitamente iniciada, liberando seu replay antigo.
Frontend não possui executable/argv/environment/cwd/PID/origin/authority como
parâmetros de criação. O backend resolve o shell pela boundary LR-9B e escolhe
HOME absoluto/canonical existente; fallback documentado `/`, sem sandbox.
`startingDirectory` é o diretório inicial factual, não uma inferência de cwd após
um `cd` no shell.

A policy interna `PtyLifecycle::HumanInteractive` desativa exclusivamente a
expiração automática da boundary `open_human_shell`. A PTY genérica continua
`Bounded`; `ExecutionRequest` conserva validação de timeout e Structured Exec
conserva deadline e MAX_TIMEOUT de 3600 s. Sessão de produto termina por `exit`,
close explícito, falha nativa ou Quit. Teste usa elapsed artificial acima de 1h;
não foi alegado endurance físico de uma hora.

`terminal_surface/SurfaceHub` possui somente a attachment visual atual e workers
bounded. Trocar Terminal → Conversation desanexa, não fecha sessão. Close
Presentation revoga a attachment antes de destruir WebViews; Destroyed também
faz detach idempotente. Reopen cria a main, cuja view inicial continua Conversation;
selecionar Terminal reencontra a mesma sessão/PID. Quit conserva shutdown e reap
LR-9B. Não há terminal persistente após restart do processo.

## Fronteira humana e segurança

Dar input a uma PTY humana concede à main o controle daquele shell durante a
attachment. **Uma main totalmente comprometida pode iniciar/anexar e operar
esse shell**. O limite é intencional, descrito em [SECURITY](SECURITY.md).
Terminal não se torna dono do processo nem cria authority agentiva; isso não é
uma promessa de que a main comprometida seja incapaz de executar comandos humanos.

Somente main possui as permissões novas; todos os handlers verificam também o
label nativo. Settings, Conversation, providers e agents não recebem/importam a
API. Componentes na mesma main não constituem uma Isolation Pattern; hardening
futuro não é vendido como implementado.

CSP permanece restritiva/local, sem script/fonte remota, unsafe-eval, worker,
iframe ou shell/filesystem/process plugin genérico. `ExecutionAuthority` nunca é
serde ou argumento IPC. SessionDto não contém environment/request/argv/PID.
TraceDto não contém ExecutionRequest/Result ou material externo ao bus. O usuário
pode imprimir segredos no shell humano; bytes PTY não são enviados a Conversation,
trace ou provider. Sem log durável de conteúdo.

## IPC e Channels

Oito commands, com permissões `allow-<nome-em-kebab-case>` no padrão AppManifest/
autogenerated existente, somente em `main-window.json`:

| Command | Contrato |
| --- | --- |
| terminal_session_status | DTO sanitizado ou null; não abre shell |
| open_human_terminal | criação/reuso padrão; nenhum seletor de programa/cwd/env |
| attach_terminal_surface | sessionId opcional; Channels PTY, status e Activity; token visual string |
| detach_terminal_surface | revoga token visual correspondente; não encerra PTY |
| acknowledge_terminal_batch | stream pty/trace + cursor exato do batch pendente |
| send_terminal_input | body raw + header x-terminal-attachment ativo; max 64 KiB |
| resize_terminal | attachment ativa + rows/cols u16 validados 1..1000 |
| close_human_terminal | sessionId humano registrado; cancellation/reap existente |

Sem executor genérico, arbitrary program/argv/env/cwd/PID, handoff ou cancelamento
por PID. IDs de sessão, attachment, trace sequence e sequence range usam decimal
string. O teste nativo aloca sessão e evento reais em `9007199254740993`, acima de
Number.MAX_SAFE_INTEGER. O codec raw também testa u64::MAX.

PTY usa `Channel<Response>` com `Response::new(Vec<u8>)`, recebido como
`Channel<ArrayBuffer>`. Frame contém header de 24 bytes: três u64 little-endian
(cursor, chunks ausentes nesta recuperação, dropped bytes cumulativos), seguido
por bytes PTY concatenados **sem alteração**. JS lê o header com BigInt e passa
Uint8Array ao `term.write`. Não há JSON array de output, evento global por chunk,
invoke de output por chunk ou bytes em React state. ANSI é responsabilidade do
emulador. [Contrato raw Tauri](https://v2.tauri.app/reference/javascript/api/namespacecore/)
e [addons xterm](https://xtermjs.org/docs/guides/using-addons/) foram conferidos,
além das versões instaladas locais e da [release estável 6.0.0](https://github.com/xtermjs/xterm.js/releases/tag/6.0.0).

Status é enviado somente quando muda, junto a um frame confirmado. Cada stream
possui **um batch in-flight**. PTY confirma pelo callback do parser xterm; Activity
confirma após o flush bounded da coleção. Send falhou ou ack não chegou em 5 s:
a attachment termina, input/resize são revogados e o Core continua. Reconnect
recebe replay desde zero em novo emulador, com gaps factuais. Nenhuma retry de
input é feita para tentar compensar perda visual.

Essas esperas acontecem em workers de Presentation, nunca no reader/publisher.
Channels em trânsito também têm budget; não basta limitar apenas a fila do Core.

## Live e recuperação

PTY live tem no máximo dois subscribers, cada um com fila de **um u64** e contador
saturating de notificações perdidas. Registration amostra cursor atomicamente com
o ring. Producer usa try_send, sem copiar output por subscriber. Drop remove
registration; detach da surface acorda os waits e libera subscribers. Uma
notificação perdida não equivale necessariamente a bytes perdidos: replay é a
fonte da recuperação e seu gap decide o conteúdo indisponível.

Trace preserva LiveSubscriber LR-9A, acrescentando somente espera bloqueante/
timeout no consumidor. Registration ocorre antes do replay para eliminar janela
de perda na transição; o worker usa notificações live para acordar e lê a retenção
priority-aware após seu cursor. Loss de live é reportada separadamente de buracos
reais de replay, incluindo buracos internos e tail perdido. Publishers continuam
try_send, sem callback, Channel, UI ou wait sob o lock do bus.

Idle: wait de 250 ms para detectar estado/detach e loss; nenhuma mensagem visual
quando nada muda. Batches ativos têm janela de 32 ms. Não há busy-loop de 60 Hz,
RAF permanente ou poller adicional do OperationalSummary.

## DTO e coalescing

TraceDto possui sequence/lastSequence strings, fragment count, timestamps de
primeira/última observação, class, sourceType/id/instance, TaskId seguro atual,
subtask/correlation, kind, code/channel e text. Enums têm mappings explícitos;
nenhum Debug é usado como protocolo. Todos os campos derivam de OperationalEvent
ou do range exato de CoalescedText.

`coalesce_batch` LR-9A é aplicado a cada batch bounded. Somente TextDelta
adjacentes e contíguos com provenance completa, coalescing key e channel iguais
concatenam; limite de 32 fragments / 32 KiB. STATE/CRITICAL e gaps quebram a
concatenação. Texto UTF-8, espaços e ordem permanecem exatos. Não há LLM, summary
inventado ou suposição de que ExecutionBroker será a única fonte futura.

As linhas fixas do viewport mostram escapes JSON reversíveis para newline/control
characters, evitando sobreposição vertical. O DTO/store e o title preservam o
texto original. Trace não é interpretado como HTML/ANSI.

## Frontend, budgets e lazy loading

Home mantém id interno `home` e label **Terminal**; a área central existente foi
reutilizada. Conversation permanece separada, inclusive como view inicial.
Activity é secundária, recolhível, com filtros por classe, fonte e TaskId.
Em largura <=740 px, tabs Shell/Activity substituem o split vertical. O painel
OperationalSummary existente continua único e conserva seu próprio lifecycle.

| Budget | Valor |
| --- | ---: |
| Registry humano de produto | 1 sessão, processo atual |
| Retenção PTY LR-9B | 2 MiB / 512 chunks |
| Live PTY | 2 subscribers × 1 cursor; nenhum clone de megabytes |
| Replay/frame PTY | 32 chunks / 256 KiB + header 24 bytes |
| Trace backend LR-9A | 1024 eventos / 2 MiB estimados, priority-aware |
| Trace live LR-9A | 64 eventos por subscriber; MAX_SUBSCRIBERS=8 |
| Trace batch | 128 eventos / 256 KiB estimados antes do coalescer |
| Bridge | 2 workers ativos + até 2 retirando; cap atômico de 4 |
| Transporte | 1 batch pendente por stream; ack deadline 5 s |
| Input | janela 8 ms, threshold 4 KiB, chunks <=64 KiB |
| Input frontend | 256 KiB queued + até 64 KiB in-flight |
| Input nativo LR-9B | 8 chunks + pending do writer; try_send |
| Resize | debounce 80 ms, serializado, último tamanho vence |
| Trace frontend | uma coleção até 1024 rows / 2 MiB de charge (512 + UTF-8 text) |
| Flush trace | 50 ms sob atividade; zero timer permanente idle |
| Viewport | row 26 px, overscan 6, cap absoluto 40 rows DOM |
| Xterm | scrollback 2000 linhas, cursorBlink=false |

Budgets de payload/charge não prometem RSS físico. Snapshot React guarda refs da
mesma coleção bounded; filtros são views, sem cópia integral de conteúdo por
filtro. Retenção frontend evicta STREAM antes de STATE e CRITICAL. Cada batch,
não cada evento, agenda update. Metadata distingue replay incompleto, entregas
live perdidas e eviction/compactação do viewport.

Input UTF-8/onBinary mantém ordem serial de bytes. Paste é dividido pelo cap
LR-9B. Excesso ou queue full são visíveis e recuperáveis; pendências são descartadas
em falha, sem retry infinito ou duplicação por outcome de transporte desconhecido.
Retomar entrada habilita novas entradas; não reenvia as anteriores.
ResizeObserver observa somente o container xterm, fit + debounce serial; não envia
cada pixel nem cria loop RAF.

Dependências novas, exatas no package e lock: `@xterm/xterm=6.0.0` e
`@xterm/addon-fit=0.11.0`, MIT, sem addon extra/framework/virtualizer dependency.
TerminalWorkspace e CSS xterm entram somente pelo React.lazy quando Terminal é
selecionado. Manifest Vite registra esse entry como dynamic. A auditoria percorre
imports estáticos de index/App/OperationalSummary e verifica ausência do emulator
**e CSS**. WebKit verifica ausência de request inicial e uma única carga JS,
inclusive após Terminal → Conversation → Terminal.

Chunks finais: TerminalWorkspace **344,26 kB JS** (aprox. **87,56 kB gzip**) e
**5,71 kB CSS** (1,52 kB gzip); valores exatos do build estão na evidência.
App permanece cerca de 50,35 kB e AvatarViewport 634,27 kB, separado/opt-in.

- LR-9D: adapters reais TaskEvent/Scheduler/TaskGraph/providers/Codex/Copilot.
